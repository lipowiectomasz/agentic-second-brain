# Secrets

A secret is any value that grants access: API keys, tokens, passwords, session secrets,
private keys, connection strings with credentials, webhook signing keys.

## Where secrets live

- **Only in untracked env files**: `.env` and `.env.<environment>` in the repository root,
  plus env files generated by third-party installers (for example `appwrite/.env`).
  `git check-ignore -v <file>` must confirm each one is ignored before the first value goes in.
- **`.env.example` is tracked and holds only variable names** with empty values or harmless
  local defaults (`http://localhost:...`). Never a real or a "test" secret.
- Compose files, Dockerfiles, CI files, `package.json` scripts and Makefiles reference variables
  (`${NAME}`, `env_file:`), never values.
- CI and servers get secrets from their secret store (CI secrets, server env file created by
  hand), never from the repository.

## Where secrets never appear

- Source code, tests, fixtures, seeds, snapshots, documentation and screenshots.
- Process arguments (`argv` is visible to other users and lands in shell history) - pass
  secrets through env or a file with mode `0600`.
- Logs, error messages, HTTP responses, audit entries and analytics. Log the variable name,
  never the value.
- Client bundles: in front-end frameworks a secret is read only in server code
  (`standards/stack/nextjs.md`).
- Commit messages, MR titles and issue text.

## Reading secrets

- One validated entry point reads the environment at start-up and fails fast with the names
  of missing variables (`standards/stack/node.md`). No `process.env.X` scattered through code.
- A script that writes secrets (bootstrap, key rotation) writes them to the env file and
  prints only which variable names it wrote.
- Generated secrets come from a cryptographic source (`crypto.randomBytes`, `openssl rand`),
  never from `Math.random` or a fixed value.

## Scope and rotation

- Every key gets the narrowest scope it needs; a key per purpose rather than one admin key
  for everything.
- A secret that reached a tracked file, a log or a chat is compromised: rotate it first, then
  clean the history. Removing the line is not enough.

## Before publishing a repository

Scan the full history, not only the working tree, with a secret scanner run in a container
(for example `gitleaks detect --source . --log-opts="--all"`). A finding blocks publication
until the secret is rotated and the history rewritten.
