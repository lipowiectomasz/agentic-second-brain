# Appwrite (self-hosted 2.x)

Self-hosted Appwrite generated by the official installer. Versions in use: 1.9.x and 2.5.0.
The notes below were confirmed on 2.5.0 unless stated otherwise.

## Pin the version to the client SDK

The server SDK targets one server line: `node-appwrite` 31 targets Appwrite 2.5.x, the line that
runs on Cloud. Generate the self-hosted stack with the same version
(`appwrite/appwrite:<version>` installer image), not with `latest`. A newer self-hosted server
than the SDK, or the other way round, shows up as missing methods or changed response shapes.

## Generate the stack, do not hand-write it

Run the installer non-interactively and without starting the stack:

```bash
docker run --rm --volume "$PWD/appwrite":/usr/src/code/appwrite:rw \
  --entrypoint=install appwrite/appwrite:2.5.0 \
  --http-port=127.0.0.1:18080 --https-port=127.0.0.1:18443 \
  --interactive=N --no-start=true --database=postgresql --domain=localhost
```

- The files are written as `root`; `chown` them to the host user afterwards.
- `appwrite/.env` holds generated secrets and must be ignored by git (`standards/core/secrets.md`).
- The installer writes `_APP_MQTT_PORT="8883"` and `_APP_MQTT_WSS_PORT="8084"`, published on
  all interfaces. Replace the lines, do not append - an appended duplicate is ignored.

## Features that are off by default

| Feature | Switch | Symptom when off |
|---|---|---|
| VectorsDB | `_APP_VECTORSDB="enabled"` in `appwrite/.env` (default `disabled`, even though the PostgreSQL it needs is in the stack) | `403 general_service_disabled` on `/v1/vectorsdb`; it is not a project service, the project services API rejects `vectorsdb` |
| Built-in embeddings | compose profile `embedding` (`--profile embedding` or `COMPOSE_PROFILES=embedding`); `_APP_EMBEDDING` stays `enabled` | no `appwrite-embedding` container; embedding calls fail |
| DocumentsDB | `_APP_DOCUMENTSDB="enabled"` | `403 general_service_disabled` |

After changing `appwrite/.env`, recreate the containers (`docker compose up -d`), a restart does
not reload the file.

## Console API for automated bootstrap

A fresh instance can be bootstrapped without clicking through the console:

| Step | Request |
|---|---|
| console account | `POST /v1/account`, header `X-Appwrite-Project: console` |
| session | `POST /v1/account/sessions/email`; keep the `a_session_console` cookie |
| organisation | `POST /v1/teams` (console project) |
| project | `POST /v1/organization/projects`, header `X-Appwrite-Organization: <id>` |
| API key | `POST /v1/organization/projects/<id>/keys` with `name` and `scopes`; the secret is returned only here |
| web platform | `POST /v1/project/platforms/web`, headers `X-Appwrite-Project: <id>`, `X-Appwrite-Mode: admin` |

"Already exists" is not reported consistently: a second console account returns
`501 user_console_count_exceeded`, a second organisation `403 organization_creation_prohibited`.
Check existence with `GET` before creating instead of interpreting error codes.

Key scope names come from the SDK enum `ProjectKeyScopes`. VectorsDB has its own scopes
(`vectorsdb.collections.*`, `vectorsdb.documents.*`, `vectorsdb.indexes.*`); `collections.*`
and `documents.*` belong to the legacy databases API.

## Calling Appwrite from other containers

- Containers on the `appwrite` network reach the API directly at `http://appwrite/v1`, without
  traefik. Keep a separate public endpoint for the browser (`http://localhost:<port>/v1`).
- The `appwrite` network is created by the Appwrite stack. A container that declares it as
  external fails to start before the stack exists - see `standards/stack/docker.md`.
- Container names in the generated file are fixed (`appwrite`, `appwrite-traefik`, ...). Two
  Appwrite stacks on one machine collide; run one at a time or rename the containers.

## Dead database connections after long uptime

After about a day of uptime the API container can keep a pool of PostgreSQL connections the
server has already closed. Every database request then fails with `500 Server Error`; the
API log shows `SQLSTATE[HY000]: General error: 7 server closed the connection unexpectedly`,
while the database container reports healthy and `/v1/health/version` still answers.
Restart the API container (`docker restart appwrite`), not the database. A schema run that
failed half-way may still have created resources - read the current state before retrying.

## Functions cannot reach the API on a local stack

`APPWRITE_FUNCTION_API_ENDPOINT` is built from `_APP_DOMAIN`; with `localhost` it points the
runtime at itself. Runtime containers sit on the `runtimes` network, where only the executor
lives, so every SDK call from a function fails with `fetch failed` (with `logging: false` you see
only a 500). Attach traefik to `runtimes` with an alias in a compose overlay and pass that address
to the function as a variable:

```yaml
services:
  traefik:
    networks:
      runtimes:
        aliases: [appwrite-api]
```

The function then uses `http://appwrite-api/v1`; the open-runtimes firewall
(`_APP_OPEN_RUNTIMES_NFT`) does not block it. On a server with a public domain the default
endpoint works and the variable stays unset.

Functions are project-wide, not per database: a test namespace in the same project needs its own
function ID if the function reads a namespace variable.

## JWTs are not tied to an existing session

`users.createJWT({ userId, sessionId })` does not check `sessionId`: a JWT minted for a deleted or
never-existing session works for `account.get` and row reads. Only a JWT minted before its session
was deleted stops working. Deleting a session is therefore not a revocation mechanism for JWTs you
mint yourself - check your own revocation state before every use and keep minted JWTs inside the
server.

What execution records keep with `logging: false` (synchronous execution): the request path with
its query string and the `content-type` and `x-appwrite-client-ip` headers; not the request body,
custom headers or the response body. The caller's address reaches the function only as
`x-appwrite-client-ip`; the dynamic key as `x-appwrite-key`.

## SDK details

- `node-appwrite` 31 has no Health service; read the version from the public
  `GET /v1/health/version`.
- Permissions are enforced only for requests with a user session or JWT; an API key bypasses
  them. Read user data with a session-scoped client, use the key for administration.
- Columns and indexes are created asynchronously. Wait for `status: "available"` before
  creating an index on new columns.
